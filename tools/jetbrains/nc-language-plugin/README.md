# nC Language Plugin (JetBrains)

## What is this plugin?

nC Language Plugin is the official JetBrains-side integration for nC. It provides file type support, syntax highlighting, color settings aligned with official nC palettes, and integration routes to ncc, nclsp and nc-sys-lsp.

Semantic authority remains in ncc.

## Version 1.0.0.21v

`1.0.0.21v` is the canonical plugin baseline. It retains live compiler diagnostics, semantic colors, completion, hover documentation, navigation, references, symbols, rename, quick fixes, Run/Debug, toolchain resolution and stable project/lane routing.

The plugin still does not own language semantics. All parser, sema, IR and machine truth remains delegated to `ncc`.

## Release-grade editor surface

- `.n`, `.nb`, `.nbb`, `.nm`, `.nbo` and `.ncp` are registered as distinct file types, not one generic bucket. Legacy `.nc` remains a compiler/LSP alias and is deliberately not claimed by the plugin.
- Basal/root, machine, primitive and kernel lanes have distinct color keys and icons.
- Kernel `.n` files need no `[@kernel]`: `name at address`, `*8` through
  `*512`, or a `kernel...` container with `main:` activates the kernel lexer;
  comments and strings are masked before detection.
- Pointer/ref/site/memRegion types are highlighted separately from ordinary types.
- Raw/risk/hazard markers are highlighted as dangerous authority.
- FFI symbols remain visually separate from runtime and compiler symbols.
- Text colors follow the Java/Python/C/C++/Rust-inspired Polyglot Systems palette:
  `.n` uses Java amber/steel plus Python blue/yellow, C standard blue,
  C++ core/light blue and Rust copper/hazard.
- Capability contract records auto-import suggestions and pointer/FFI support for marketplace review.
- Capability contract records the `c_cpp_rust_java_grade` parity tier and the required professional IDE surfaces.
- Completion predicts compact import families, imported runtime/heap functions,
  struct fields, aggregate element fields, sibling project modules and
  `ref main ->> run` entrypoint references.
- `.nm`, `.nb`, `.nbb` and `.ncp` are manual surfaces: completion, prediction,
  snippets, predictive inlays and generic fallback are disabled while colors, navigation and
  diagnostics remain active.
  Machine filters registers and instructions through `target.arch` and resolves
  local symbols; Basal and Primitive resolve document declarations without
  leaking vocabulary from another low-level mode.

## Supported file extensions

- `.n`: normal nC high-level/runtime/compiler surface.
- `.nc`: legacy compiler/LSP alias; no JetBrains file-type ownership.
- `.nb`: basal/root source.
- `.nbb`: Primitive material and NBB binary surface.
- `.nm`: machine/ASM surface.
- `.nbo`: read-only backend object IR retained in `.ncc/lowering`.
- `.ncp`: physical hardware, firmware and capability surface.

## Boundaries

- The plugin does not replace ncc.
- The plugin does not invent semantic validation.
- QEMU evidence remains emulated evidence, not physical certification.

## Run configurations

Project run configurations can be generated by the toolchain:

```bash
ncc ide init --ide jetbrains
```

The generated `.idea/runConfigurations/*.xml` entries expose Run, Check and Format actions for the active file and delegate to `ncc`.

The plugin also registers a native JetBrains Run Configuration type named `nC`.
It detects runnable `.n`, `.nb`, `.nbb` and `.ncp` files, resolves `ncc`
from the installed nC suite, a compatible `ncup` result, PATH or a workspace
build, and exposes profile, target, CC ABI, entry, linker and show-return fields.
Machine `.nm` remains editable, highlighted, navigable and checkable, but is not
admitted by Run/Debug; start it explicitly with `ncc machine ...` in a terminal.
Every candidate must expose `stoud::memory::map` and the closed native
debug-adapter protocol. Stale project-local compilers are rejected instead of
silently taking precedence.

Actions:

- `nC: Run Active File`
- `nC: Debug Active File`

Debug launches through the JetBrains Debug executor with `NCC_IDE_DEBUG=1` and
requires the same resolved compiler to expose `ncc debug-adapter`. `nide init`
also generates
`.ncc/ide/nc-debug-adapter.cmd` or `.sh` for source-map probing and stdio DAP
launches from the same resolved toolchain for runnable high-level, basal,
primitive and hardware sources. Machine inspection, register snapshots and
attach/detach remain terminal operations through `ncc machine debug-bridge` and
`ncc machine debug-attach`; `.nm` never enters the JetBrains Run/Debug path.
