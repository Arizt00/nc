| Command | Purpose |
|---|---|
| `ncc machine doctor` | status |
| `ncc machine targets --json` | target matrix |
| `ncc machine registers x86_64 --json` | register model |
| `ncc machine instructions x86_64 --json` | instruction model |
| `ncc machine abi sysv64 --json` | ABI model |
| `ncc machine interop <file.n> --target <target> --json [--strict]` | `.n` to machine interop gate |
| `ncc machine check <file.nm>` | verifier |
| `ncc machine report <file.nm> --json/--md` | report |
| `ncc machine emit-ir <file.nm> --json` | MachineIR projection |
| `ncc machine emit-bytes <file.nm> --out <file.bin>` | encoded bytes |
| `ncc machine run-bytes <file.nm-or-bin> [--raw-bin] --expect-return <i64> --timeout-ms <ms> --json` | isolated executable-memory byte runner |
| `ncc machine emit-object <file.nm> --target <target> --out <file.o>` | object emission |
| `ncc machine emit-wasm <file.nm> --target wasm32-unknown-unknown --out <file.wasm>` | WASM module emission |
| `ncc machine verify-object <file.o> --json` | object verification |
| `ncc machine link-smoke <file.nm> --target <target> --json` | local executable/link smoke through host toolchain harness |
| `ncc machine link-smoke <file.nm> --target <target> --system-loader --expect-exit <code> --json` | final Phase12 executable smoke through the OS loader (PE64/Windows, ELF64/Linux, Mach-O/macOS) |

| `ncc machine target-family-gate` | Level 6 target-family evidence gate |

## Byte Materialization vs Execution

`ncc machine emit-bytes <file.nm> --out <file.bin>` only encodes the machine instruction stream and writes those bytes. It is the inspection/materialization route: no loader, imports, process image or execution is implied.

`ncc machine run-bytes <file.nm-or-bin>` is the direct JIT/loader route for self-contained bytes. It validates the input, rejects externs and relocations for `.nm`, allocates writable memory, copies the bytes, switches the page to executable read-only, flushes the instruction cache where the host requires it, calls offset 0 as `extern-C fn() -> i64`, captures the return value and runs inside an isolated child process. The JSON payload retains `loader_contract`, `input_contract`, `execution_contract`, timeout, byte hash, memory backend, W^X policy and temp cleanup status. A crash in generated bytes is reported as `E_MACHINE_JIT_CHILD_001` by the parent, and a non-returning byte stream is killed as `E_MACHINE_JIT_TIMEOUT_001`.

`ncc machine emit-object ...` wraps the encoded bytes and relocations into a real object file for the selected target. `ncc machine build-exe ...` and the normal native `.n` route add the final executable container, imports/IAT where needed, relocations, section permissions and loader-facing headers.

For Windows PE64, the checked executable routes are:

```text
.n  -> retained .nm bridge -> .obj -> .entry.obj -> PE32+ .exe -> OS loader execution
.nm -> original source     -> .obj              -> PE32+ .exe -> OS loader execution
```

A handwritten `.nm` remains the authoritative Machine source. `ncc build` and
`nbuild` consume it in place and never duplicate it under `.ncc/code` or
`.ncc/lowering`; generated objects, executables, maps and manifests remain under
the selected artifact root. IDEs may edit and check `.nm`, while Run/Debug starts
only from explicit terminal commands.

Canonical Machine sources use `name :: machine {`. For that spelling, `name`
must match the file stem byte for byte, including case. The compatibility parser
still reads historical `name[@machine] {` fixtures, but generators only emit the
canonical form.

Normal `.n` lowering first materializes `.ncc/root/<unit>.nb` and its checked
`NBB0` binary `.ncc/root/<unit>.nbb`. It then retains two distinct representations under
`.ncc/lowering`: `<unit>.nm` is the readable, checked Machine bridge and
`<unit>.backend-object.nbo` is the structured backend object text containing
sections, symbols and relocations. The NBO header names the Basal root and its
Machine source; the `.nm` embeds the final NBO SHA-256, and the build manifest
records both hashes without a circular digest. `.ncc/code` remains reserved for
project identity JSON and user launchers.

The portable ISA catalog includes the existing x86_64 profiles plus x86 ADX
and hardware random generation, ARMv7 Thumb-2 DSP saturation, AArch64
EXTR/UBFM/SBFM/BFM, RV32/RV64 Zbb+Zbs and the WASM32 integer, comparison,
bit-operation, sign-extension, memory and memory-growth set.
Each admitted form is covered by encoding and internal disassembly.

The normal `.n` run/build surface must keep the first 32 bytes of Win64 call shadow space separate from local stack slots before any runtime/import call such as `malloc`, `printf`, `WriteFile` or `ExitProcess`.
